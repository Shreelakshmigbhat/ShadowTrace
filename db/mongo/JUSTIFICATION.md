# Why forensic artifact metadata lives in MongoDB

The metadata extracted from evidence has a different shape for every evidence type. A phone image yields an IMEI, an OS version and a list of installed apps. A disk image yields partitions with file systems and sizes. A network capture yields protocols and per-IP byte counts, and an email archive yields a mailbox and a date range. New evidence types such as drone logs or cloud exports will bring fields nobody can list in advance. Four relational designs could hold this, and each fits poorly. An Entity-Attribute-Value table (`evidence_id, attr_name, attr_value`) stores everything as strings, so it loses data types, CHECK and NOT NULL constraints, and foreign keys. It also turns a single question such as "list the apps on phone X" into many self-joins or pivots, and a nested structure like partitions inside a disk image has to be flattened with invented keys. One wide table with dozens of nullable columns (`imei`, `filesystem`, `protocols`, ...) leaves most cells NULL for any given row, needs an `ALTER TABLE` whenever a new evidence type appears, and hides the rule "only mobile devices have an IMEI" because the database cannot express it. A MySQL `JSON` column removes the schema problem, but MySQL cannot validate its contents beyond JSON syntax, and indexing an array of tags needs generated columns or multi-valued indexes that are awkward to write. Aggregating inside arrays (for example the most common installed apps) needs `JSON_TABLE` gymnastics. MongoDB stores each artifact as one self-describing document in which arrays and sub-documents are native. It validates the document with `$jsonSchema`, so a Mobile Device document must carry an IMEI while a Disk Image document must carry partitions, and it indexes array elements directly (multikey indexes on `tags` and `findings.severity`). It also aggregates inside arrays with `$unwind` and `$group` in a few readable lines. The integrity-critical facts stay in MySQL (who held the evidence, when, and the audit trail), where foreign keys, transactions and triggers matter, and each Mongo document points back to them through `evidence_id`.
